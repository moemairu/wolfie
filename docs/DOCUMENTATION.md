<h2 id="architecture">🏗️ 1. Architecture</h2>

Wolfie is built on a lightweight, zero-dependency philosophy. It eschews heavy frameworks and build pipelines in favor of native web APIs and standard library tools.

### System Diagram

```mermaid
graph TD
    A[Cowrie Honeypot] -->|Writes NDJSON| B(cowrie.json)
    
    subgraph Wolfie Relay Server
        B -->|Tails & Parses| C[server.py]
        C -->|Serves Static Files| D(HTML/CSS/JS)
        C -->|REST API| E(Aggregated JSON)
        C -->|SSE Stream| F(Real-time Events)
    end
    
    subgraph Browser Client
        D --> G[Wolfie Dashboard]
        E -->|fetch()| G
        F -->|EventSource| G
    end
```

### 1.1 The Relay Server (`server.py`)

Cowrie writes its logs locally. Browsers cannot read local server files or establish persistent file-tailing connections. The Relay Server bridges this gap.

It is a single, zero-dependency Python script (`server.py`) utilizing Python's built-in `http.server` and `threading`.

**Responsibilities:**
1. **Static File Serving**: Serves the frontend assets.
2. **REST API**: Parses `cowrie.json`, computes statistics (e.g. total sessions, success rate), aggregates sessions, and returns JSON.
3. **SSE Streaming**: Maintains long-lived HTTP connections using Server-Sent Events (SSE). It polls `cowrie.json` for new lines and pushes them to connected clients instantly.

### 1.2 The Frontend Application

The frontend is a pure Vanilla JS Single Page Application (SPA).

**Core Systems**
*   **`js/main.js`**: The application bootstrap. Initializes the router, sidebar, and SSE connection.
*   **`js/router.js`**: A simple hash-based client-side router (`#/dashboard`, `#/sessions`, etc.).
*   **`js/state.js`**: A lightweight global state manager utilizing the native `EventTarget` API. Dispatches events like `stateChange` and `newEvent` (when SSE pushes data).
*   **`js/api.js`**: The data abstraction layer. Fetches data from the Relay Server's REST endpoints and handles cache invalidation.
*   **`js/sse.js`**: Manages the `EventSource` connection to the Relay Server, automatically pushing new events to the global state.
*   **`js/utils.js`**: Shared utilities, primarily HTML sanitization (`escapeHtml`) to prevent Cross-Site Scripting (XSS) from attacker-controlled payload data.

**Component Structure**
The UI is divided into two types of modules:
1.  **Pages (`js/pages/`)**: Full-screen views (e.g., Dashboard, Activity, Session Detail). Pages coordinate data fetching and layout.
2.  **Components (`js/components/`)**: Reusable UI elements (e.g., `stat-card.js`, `activity-feed.js`, `command-timeline.js`). Components are pure functions that take data and return HTML strings.

### 1.3 Security Considerations

Since Wolfie displays raw data generated by malicious actors (e.g., usernames, passwords, terminal commands, URLs), **Cross-Site Scripting (XSS) prevention is critical**.

The architecture enforces strict sanitization:
- `utils.js -> escapeHtml()` must wrap every piece of attacker-controlled data before it is interpolated into HTML strings.
- URLs (for file downloads) are validated using `sanitizeUrl()` to prevent `javascript:` URI injection.

<h2 id="cowrie-analysis">🕵️ 2. Cowrie Analysis & Knowledge Base</h2>

### 2.1 Cowrie Overview
Cowrie is a medium to high interaction SSH and Telnet honeypot designed to log brute force attacks and shell interactions performed by an attacker.
- **Medium Interaction (Shell)**: Emulates a UNIX system in Python. Features a fake filesystem, saves downloaded/uploaded files, and captures commands.
- **High Interaction (Proxy)**: Functions as an SSH and Telnet proxy to observe attacker behavior to another backend system or pool of QEMU virtual machines.
- **LLM Backend**: Dynamically generates responses to attacker commands using Large Language Models like OpenAI GPT.

Cowrie provides rich JSON logging of events, stores TTY logs in a UML-compatible format for replay, and can be integrated with various output modules.

### 2.2 Event Catalog & Dashboard Data Mapping

| Event ID | Description | Available Fields | Dashboard Usage |
|----------|-------------|------------------|-----------------|
| `cowrie.session.connect` | New connection established | `src_ip`, `src_port`, `dst_ip`, `dst_port` | Live Activity Feed, Dashboard Session Counts |
| `cowrie.login.success` | Successful authentication | `username`, `password` | Auth Attempts, Live Feed, Session Details |
| `cowrie.login.failed` | Failed authentication | `username`, `password` | Auth Attempts, Credential Leaderboards |
| `cowrie.command.input` | Command line input | `input` | Commands Table, Session Details, Live Feed |
| `cowrie.command.failed` | Command line input failed | `input` | Commands Table, Session Details |
| `cowrie.session.file_download` | File downloaded to Cowrie | `url`, `outfile`, `shasum` | Downloads Page, Malware Tracking |
| `cowrie.session.file_upload` | File uploaded to Cowrie | `filename`, `outfile`, `shasum` | Downloads/Uploads Page |
| `cowrie.virustotal.scanfile` | File scanned via VT plugin | `sha256`, `positives`, `total`, `is_new`, `scans` | Threat Intelligence, Downloads Page |
| `cowrie.log.closed` | TTY Log closed (session replay data) | `duration`, `ttylog`, `size`, `shasum`, `duplicate`| Session Replay, Session Details |
| `cowrie.session.closed` | Session disconnected | `duration` | Session Details, Activity Feed |
| `cowrie.client.version` | SSH identification string | `version` | Client Information |
| `cowrie.client.fingerprint` | SSH public key auth attempt | `username`, `fingerprint`, `key`, `type` | Client Information |
| `cowrie.client.kex` | SSH Key Exchange attributes | `hassh`, `hasshAlgorithms`, `kexAlgs`, `keyAlgs` | Client Information |
| `cowrie.client.size` | Terminal window size | `width`, `height` | Client Information |
| `cowrie.direct-tcpip.request` | Proxy forwarding request | `src_ip`, `src_port`, `dst_ip`, `dst_port` | Threat Tracking |
| `cowrie.direct-tcpip.data` | Data sent through forwarding | `dst_ip`, `dst_port` | Threat Tracking |

*(Note: All events share common attributes: `message`, `sensor`, `timestamp`, `src_ip`, `session`)*

### 2.3 Session Replay Mapping
Session replay requires TTY logs generated by the `cowrie.log.closed` event.
- **Data available**: `duration`, `size`, `shasum`, and the `ttylog` filename (stored in `var/lib/cowrie/tty/`).
- **Wolfie integration**: The dashboard extracts raw commands from event logs (`cowrie.command.input`) to build a chronological command timeline in the UI without needing to parse the binary `ttylog` format directly.

### 2.4 Configuration Mapping
Cowrie's configuration (`cowrie.cfg`) is managed in sections. Key configurations for Wolfie to potentially manage in the future:
- `[honeypot]`: `backend` (shell, proxy, llm), `contents_path`, `txtcmds_path`.
- `[telnet]`: `enabled`, `listen_endpoints`.
- `[ssh]`: `listen_endpoints`, `forward_tunnel`.
- `[llm]`: `api_key`, `model`, `max_tokens`.
- `[output_json]`, `[output_virustotal]`: output module toggles and settings.
